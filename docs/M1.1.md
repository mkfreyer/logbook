# M1.1 — préparer les exercices et les séries

## Ce que permet cette version

M0 a été validé par l'utilisateur sur un véritable iPhone avec Expo Go. M1.1 part de cette version et ajoute la configuration d'une séance prévue, sans commencer l'entraînement en direct. Les programmes, séances planifiées, confirmations de suppression et swipes verticaux M0 sont conservés.

Depuis les séances d'un programme, ouvrir une séance pour consulter ses exercices et leurs séries prévues. La bibliothèque permet de rechercher des exercices réels et de créer un exercice personnalisé. Aucun programme d'entraînement n'est installé automatiquement. Ajouter un exercice à une séance crée une occurrence prévue distincte de sa fiche de bibliothèque : le même exercice peut être utilisé dans plusieurs séances, ou plusieurs fois dans une même séance.

Les exercices prévus peuvent être modifiés, déplacés avec les commandes Monter/Descendre ou supprimés après confirmation. Chaque exercice possède une liste de séries, avec les mêmes possibilités d'ajout, modification, réorganisation et suppression. Les identifiants restent stables lors des modifications et changements d'ordre. Supprimer un exercice de la séance supprime ses séries prévues, mais conserve sa fiche dans la bibliothèque et les autres exercices.

La création personnalisée ajoute d'abord une fiche à la bibliothèque ; l'utilisateur choisit ensuite de l'ajouter à sa séance. Un exercice personnalisé peut aussi être renommé ou corrigé depuis sa configuration, avec le même identifiant : ses utilisations planifiées reflètent cette correction sans recréer les séries. Changer l'exercice prévu conserve la position, les consignes et les séries de cette occurrence ; l'interface invite à vérifier les cibles, notamment si le matériel ou la convention de charge change.

Le design reprend les écrans **05** (vue d'ensemble), **09** (champs de série) et **19** (bibliothèque) de la [maquette validée](design/Maquette%20d’application%20fitness%20complète%20en%2021%20écrans.png). La vue d'ensemble décrit uniquement la préparation. Aucun tonnage, résultat, durée réalisée ou démarrage factice n'est présenté.

## Une configuration indépendante pour chaque série

| Champ | Comportement |
| --- | --- |
| Type | Travail, échauffement, top set, back-off ou personnalisée. Le type n'applique aucune progression automatique. |
| Étiquette | Facultative et libre, jusqu'à 80 caractères. Sans étiquette, un numéro ou le type identifie la série. |
| Répétitions | Nombre exact ou plage minimum/maximum ; valeurs entières non négatives, maximum au moins égal au minimum. |
| Charge cible | Facultative, en kilogrammes, non négative. La saisie accepte un point ou une virgule décimale. Un champ vide reste sans objectif de charge. |
| RIR cible | Facultatif ; entier de 0 à 10 pour cette première version. Le RIR désigne les répétitions estimées encore possibles en fin de série. Ce plafond de saisie est une borne pratique du prototype, sans recommandation sportive automatique. |
| Repos après cette série | Valeur propre à la série, en secondes entières de 0 à 86 400. Zéro signifie qu'aucun repos n'est prévu. |
| Notes | Facultatives, jusqu'à 1 000 caractères. |

Le repos n'existe **pas comme réglage global de l'exercice**. Trois séries peuvent donc garder respectivement 60, 120 et 180 secondes, même après réorganisation. Le repos est enregistré sur la série qui précède l'intervalle. Une valeur peut aussi être conservée sur la dernière série comme objectif de préparation ; M1.1 ne démarre aucun minuteur et ne décide pas automatiquement du passage entre exercices.

La convention de charge est explicite dans chaque fiche d'exercice : **charge totale**, **charge par haltère** ou **charge ajoutée** pour un éventuel lest. Les exercices personnalisés demandent ce choix. Une charge ajoutée n'inclut pas automatiquement le poids du corps. Aucune comparaison de tonnage entre ces conventions n'est calculée ici.

## Stockage et migrations

Le fichier SQLite reste **`logbook.db`**, avec la même identité de projet Expo. La migration de version 1 vers version 2 s'effectue dans une transaction : elle ajoute les tables nécessaires et leur catalogue réel, sans reconstruire les tables ni effacer les lignes M0. Une erreur annule la migration et laisse la version précédente en place.

| Table | Rôle et relations |
| --- | --- |
| `programs`, `workout_templates` | Tables M0 conservées. Une séance prévue appartient à un programme. |
| `exercise_catalog` | Fiches stables de bibliothèque, initiales ou personnalisées ; indépendantes des programmes. |
| `workout_exercises` | Occurrences ordonnées dans une séance prévue ; référence vers sa fiche de bibliothèque. |
| `set_templates` | Séries prévues ordonnées dans une occurrence d'exercice ; objectifs de répétitions, charge, RIR et repos. |

Les suppressions en cascade concernent uniquement la préparation : programme → séances prévues → exercices prévus → séries prévues. Elles ne suppriment pas les fiches de bibliothèque. La clé étrangère vers une fiche empêche de retirer un exercice encore référencé. Les réorganisations sont atomiques et vérifient que tous les identifiants appartiennent au bon parent, sans dupliquer ni perdre une ligne. Les saisies sont validées dans les formulaires, le repository et les contraintes SQLite. Les mutations évitent les doubles validations ; une erreur reste affichée sur l'écran concerné.

Les tables ajoutées ne contiennent que des **valeurs programmées**. Pendant M1.2, une séance réellement commencée devra prendre un instantané de cette préparation et conserver ses valeurs réellement réalisées dans des entités séparées. Les historiques ne devront pas être supprimés par cascade depuis ces modèles modifiables : un éventuel lien vers leur origine restera facultatif. Aucune table d'entraînement réalisé ni faux historique n'est créé dans M1.1.

Après ouverture de M1.1, la base sur l'iPhone est en version 2. L'ancien code M0, qui connaît seulement la version 1, refuse alors de l'ouvrir et demande une mise à jour, sans effacer les données. Pour poursuivre les essais avec cette base, garder la branche M1.1 ; changer seulement la branche de l'ordinateur ne rétrograde pas SQLite.

## Emplacements du code

| Emplacement | Rôle |
| --- | --- |
| `src/domain/training.ts` | Types des fiches, occurrences d'exercices et séries prévues, conventions de charge. |
| `src/db/migrations.ts`, `exerciseCatalog.ts` | Migration version 2 et catalogue initial d'exercices réels. |
| `src/db/trainingRepository.ts` | Recherche, créations, modifications, suppressions et réorganisations SQLite. |
| `src/store/TrainingProvider.tsx` | Accès au repository sur la base déjà utilisée par M0. |

| `app/programs/[id]/workouts/` | Routes des séances et de leur préparation. |
| `tests/` | Tests de données, migrations, formulaires et régressions M0. |

Les sous-écrans restent hors du conteneur vertical des univers. Le code des swipes validés sur iPhone n'est pas modifié.

## Vérifications et essai sur appareil

Avec Node.js 24, dans le dossier du projet :

```bash
npm ci
npm run typecheck
npm test
npm run export:ios
```

Les tests vérifient une migration sur une base contenant des programmes M0, l'intégrité des relations, la création et modification des objectifs indépendants, les changements d'ordre, les suppressions et la persistance après réouverture. Les tests existants de programmes, séances, confirmations et navigation restent exécutés.

La disposition a aussi été inspectée avec les vrais composants et styles React Native Web dans un harnais temporaire hors du dépôt : vue de séance, bibliothèque et grille de configuration à 375 × 667 et 390 × 844, avec texte agrandi simulé. Ce contrôle de largeur ne reproduit pas UIKit, Dynamic Type ou le clavier natif iOS.

L'export iOS assemble JavaScript et ressources pour iOS ; il ne produit pas une application native `.ipa`. Les événements natifs, l'animation, les claviers et les alertes des tests d'interface sont simulés. Un résultat automatisé positif ne remplace donc pas l'essai sur le véritable iPhone. Le [guide M1.1](TESTER_M1_SUR_IPHONE.md) décrit ce parcours, en commençant par la conservation des données M0 et le contrôle des swipes.

## Suite M1.2

La prochaine tâche développera l'entraînement en direct : démarrage explicite, **une seule série active à la fois**, saisie des répétitions, charge et RIR réellement réalisés, sauvegarde progressive et reprise après fermeture. Le repos utilisera l'objectif propre à chaque intervalle et mesurera la durée réellement écoulée. Le passage à la série suivante restera une action de l'utilisateur ; l'expiration du repos ne changera pas automatiquement d'écran.

Le chronomètre, la pause et les alertes nécessiteront des essais iOS spécifiques. La politique exacte de repos entre deux exercices et de comptabilisation des pauses reste à préciser avant leur implémentation. Les historiques avancés, graphiques, bilan sportif, substitutions exceptionnelles, 3D, Cardio, coach et progression automatique restent hors de cette tâche.
